C4 Model Reference

Understand the layers behind EDDA’s architecture diagrams

The C4 model is a developer-friendly way to describe and visualize software architecture. It uses a small set of abstractions and diagram types so you can zoom from high-level context down to code. EDDA generates and displays C4-style views of your systems—this reference explains what each layer means.

What is the C4 model?

The C4 model was created by Simon Brown. The “C4” stands for four levels of static structure diagrams: Context, Containers, Components, and Code. Each level is a different “zoom” into the system:

  • Context — The system and its users and external systems.
  • Containers — Applications and data stores inside the system.
  • Components — Functional building blocks inside a container.
  • Code — Classes, interfaces, and other code elements (optional; often omitted).

You don’t need to use all four levels—system context and container diagrams are enough for many teams. The model is notation- and tool-independent, so it works with any diagramming style.

The four layers

Level 1

System context (Context)

The software system is the top-level abstraction: something that delivers value to its users (human or not). A system is typically what a single team builds, owns, and can change—often corresponding to one codebase or repository. The system context diagram shows:

  • Your software system (the one you’re modelling)
  • Users / actors — people or systems that use it
  • External systems — other software systems yours depends on or that depend on you

In EDDA, the enterprise view shows multiple software systems (and their relationships); selecting a system and viewing its “system” diagram is the context-level view for that system.

Level 2

Containers

In C4, a container is not Docker—it’s an application or a data store that must run for the system to work. It’s the boundary around running code or stored data. Examples:

  • Server-side web app (e.g. Spring, ASP.NET, Node.js)
  • Client-side web app (e.g. Angular, React in the browser)
  • Mobile app, desktop app, CLI, batch job
  • Serverless function
  • Database, blob store, file system

If you have a server-rendered app that also sends a large JavaScript front-end, that’s often two containers (server + client) because they run in different process spaces and communicate over the network. In EDDA, the container diagram appears when you drill into a system and shows its containers and how they depend on each other.

Level 3

Components

A component is a grouping of related functionality behind a clear interface. Components are not deployable by themselves—they live inside a container and run in the same process. In object-oriented code, a component is often a set of classes behind an interface; in other languages it might be a module or a set of functions.

Component diagrams zoom into one container and show how its responsibilities are split into components and how they interact. In EDDA, when you open a container’s detail view, you can see its components and their responsibilities, with dependencies between containers still visible at the graph level.

Level 4

Code (optional)

The code level zooms into a component and shows the actual building blocks: classes, interfaces, functions, etc. Many teams skip this level and keep architecture at context, container, and sometimes component level. EDDA focuses on system, container, and component levels; code-level diagrams are typically produced by IDEs or dedicated code-visualization tools.

How EDDA uses C4

EDDA analyzes your repositories and infers a C4-style model stored in a graph (VAULT). The READER UI lets you explore:

  • Enterprise — multiple systems and relationships (above single-system context)
  • System — one system and its containers (context + container level)
  • Container — one system’s containers and their dependencies; drill into a container to see its components

So you get the equivalent of C4 context and container diagrams, plus component details where SCRIBE has extracted them. The diagram notation (shapes, colors, optional AWS-style icons) is designed to be consistent with C4’s idea of hierarchical, zoomable architecture.

For the full specification, extra diagram types (e.g. system landscape, dynamic, deployment), and FAQs, see c4model.com.
